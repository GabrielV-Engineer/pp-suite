## 1. Project Overview & Non-Goals

### Vision
A tiny task list that runs only on the owner's own computer. The owner types a task, sees it in a list, ticks it off when finished, and can delete it. There is no account, no login, no sync and no hosting: the app starts with one command, listens only on `127.0.0.1`, and stores everything in one SQLite file (`data/tasks.db`). It exists to find out whether the owner actually uses a task list they built themselves, before investing in anything bigger.

### Users
| Persona | What they come to do | Frequency |
|---|---|---|
| The owner (exactly one person, on one computer) | Add a task, scan the list, mark tasks done, delete mistakes | Daily |

### Goals — v1 scope
1. The owner can add a task with a title of 1–200 characters.
2. The owner sees all live tasks in one list: open tasks first (newest on top), done tasks below.
3. The owner can mark a task done and undo that.
4. The owner can delete a task; the row stays in the database file (soft delete) but disappears from the list.
5. The server is reachable only from the owner's own machine (`127.0.0.1`).
6. Light and dark appearance follows the operating system automatically.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| Accounts, login, sessions | Only one person uses it, on their own machine; auth adds a schema, a test surface and no value | The owner wants to use it from a phone or another computer |
| Hosting, deploy pipeline, domain, CI | Local-only by decision; nothing to host | The owner asks for online access |
| Offline mode, sync, multi-device | Single computer, always-local data | Same trigger as hosting |
| Reminders, notifications, due dates | Explicitly declined by the owner | The owner reports forgetting tasks even though they use the list daily |
| Projects, tags, priorities, search, drag-reorder | "Nothing fancy" — the list is the whole product | The list regularly exceeds ~50 live tasks |
| Editing a task's title | Not requested; delete and re-add covers it for a prototype | The owner reports re-typing tasks more than once a week |
| A trash / restore screen | Delete is soft only so a mistake is recoverable by hand in the database file | The owner deletes something by mistake twice |
| Auto-start at login | Adds OS-specific service files; v1 starts with one command | The owner finds starting it by hand is the reason they stop using it |

**The builder must not implement anything in this table**, even if it seems like a small addition while working on an adjacent step. If a step appears to require a non-goal, that is a blueprint defect — stop and report it.

### Success metrics
| Metric | Target | How measured |
|---|---|---|
| Days with at least one task created | ≥ 7 distinct days by 2026-11-08 | Open `data/tasks.db` in any SQLite viewer and run: `select count(distinct date(created_at/1000,'unixepoch','localtime')) from tasks;` |
| Build gate | `§20.1` green | Run the §20.1 command list on a clean checkout |

## 2. Tech Stack

**Runtime track: TypeScript / Node.** This table names choices, not versions. Every version pin lives in §11.

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime | TypeScript on Node.js (the LTS line pinned in §11) | One language end to end; the track's documented setup. Rejected: Python/Flask — a second ecosystem for no gain on a UI-first app |
| Framework | Next.js (App Router) with React | Page and server code in one project and one process. Rejected: a Vite SPA plus a separate API — two processes to start for a one-page app |

| ORM / data access | Drizzle ORM with the `better-sqlite3` driver | Schema is code, migrations are generated, synchronous driver keeps queries trivial. Rejected: Prisma — heavier client for one table |
| Auth | NOT APPLICABLE | Server binds to loopback only; there is one user |
| Background work | NOT APPLICABLE | No jobs, no reminders |
| Payments | NOT APPLICABLE | Free personal tool |
| File storage | NOT APPLICABLE | No uploads |
| Email / notifications | NOT APPLICABLE | Declined by the owner |

## 4. Data Model

### Entities

**Task** — one thing the owner wants to do. Created open, may be completed and reopened any number of times, soft-deleted once.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | text | PK, not null | UUID generated in code (`crypto.randomUUID()`); safe to put in forms |
| `title` | text | not null | Trimmed, 1–200 characters; enforced at the action boundary (§5) |
| `is_done` | integer (boolean) | not null, default 0 | 1 when done |
| `created_at` | integer (ms epoch) | not null, default `unixepoch()*1000` | Set explicitly in code; drives ordering |
| `updated_at` | integer (ms epoch) | not null, default `unixepoch()*1000` | Set in code on every mutation |
| `completed_at` | integer (ms epoch) | nullable | Set when marked done, cleared when reopened |
| `deleted_at` | integer (ms epoch) | nullable | Non-null = soft-deleted; every read filters `deleted_at is null` |

No `user_id`: single-user by decision (see §20.3 decision 4).

### Relationships
None. One table.

### Indexes
| Table | Index | Why |
|---|---|---|
| `tasks` | `idx_tasks_deleted_at_created_at` on (`deleted_at`, `created_at`) | The list query filters on `deleted_at` and sorts on `created_at` |

### Schema
The builder pastes this into `src/server/db/schema.ts` (step 2). It imports only `drizzle-orm` so `drizzle-kit` can load it without path aliases.

```ts
import { sql } from "drizzle-orm";
import { index, integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const tasks = sqliteTable(
  "tasks",
  {
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    title: text("title").notNull(),
    isDone: integer("is_done", { mode: "boolean" }).notNull().default(false),
    createdAt: integer("created_at", { mode: "timestamp_ms" })
      .notNull()
      .default(sql`(unixepoch() * 1000)`),
    updatedAt: integer("updated_at", { mode: "timestamp_ms" })
      .notNull()
      .default(sql`(unixepoch() * 1000)`),
    completedAt: integer("completed_at", { mode: "timestamp_ms" }),
    deletedAt: integer("deleted_at", { mode: "timestamp_ms" }),
  },
  (table) => [
    index("idx_tasks_deleted_at_created_at").on(table.deletedAt, table.createdAt),
  ],
);
```

### Migrations
Tool: `drizzle-kit`. Change `schema.ts`, run `pnpm db:generate` (the tool names the file), review the SQL, run `pnpm db:migrate`. Migration files are committed and never hand-edited. Migrations are an explicit command, never run on app boot. There is one table and no production, so no expand-then-contract ceremony is needed in v1.

### Seed data
None. A fresh database is empty and the UI shows its empty state. E2E tests insert rows directly with `tests/helpers/e2e-db.ts` (step 6).

## 5. API Design

There is no HTTP API for the owner's data: the UI talks to the server through Next.js server actions. One route handler exists for health checks.

### Conventions
- Base path: n/a. Server actions are called by the framework; the route handler lives at `/api/health`.
- Response envelope: actions return `Promise<void>` (toggle, delete) or `Promise<AddTaskState>` (add, `{ error: string | null; title: string }`). The health route returns JSON `{"status":"ok"}`.
- Error codes: n/a. Validation errors surface as the `error` string in `AddTaskState`; invalid ids on toggle/delete are ignored silently (no row changes).
- Validation: `zod`, schemas in `src/lib/validation.ts`, applied in `src/app/actions.ts` before any query.
- Pagination: none. The list is unbounded in v1 (see Non-Goals, "exceeds ~50 live tasks").
- Idempotency: toggle sets an explicit target state (`isDone=true|false`), so a repeated submit is harmless; delete on an already-deleted task changes nothing.
- Rate limits: none (loopback only).

### Routes
| Method | Path | Description | Auth | Rate limit |
|---|---|---|---|---|
| GET | `/api/health` | Returns 200 `{"status":"ok"}`; used by `scripts/verify-server.sh` | none (loopback) | none |
| POST (server action) | `/` | `addTaskAction` — create a task | none (loopback) | none |
| POST (server action) | `/` | `toggleTaskAction` — set done / not done | none (loopback) | none |
| POST (server action) | `/` | `deleteTaskAction` — soft delete | none (loopback) | none |

### Critical endpoints — full detail

**`addTaskAction(prev, formData)`** — request: form field `title` (string). Rules: trim; length 1–200 after trim; non-string → error `Enter a task.`; empty → `Enter a task.`; over 200 → `Keep it under 200 characters.`. Success: inserts one row (`is_done=0`, `deleted_at` null), calls `revalidatePath("/")`, returns `{ error: null, title: "" }`. Failure: writes nothing, returns `{ error, title: <submitted text as string> }` so the field keeps what the owner typed.

**`toggleTaskAction(formData)`** — fields `id` (uuid), `isDone` (`"true"` or `"false"`). Sets `is_done`, sets `completed_at` to now when true and null when false, sets `updated_at`. Invalid id or unknown/deleted task: no change. Always ends with `revalidatePath("/")`.

**`deleteTaskAction(formData)`** — field `id` (uuid). Sets `deleted_at` and `updated_at` to now if the task is live. Invalid id or already deleted: no change. Always ends with `revalidatePath("/")`.

## 6. Frontend Architecture

### Routes
| Route | Page | Data source | Auth |
|---|---|---|---|
| `/` | Task list (heading, add form, list) | server query `listTasks(getDb())` at request time | none (loopback) |
| `/api/health` | health JSON | static | none |

### Rendering strategy
`/` is rendered **per request**. The page shell (`page.tsx`) is static; `TaskList` is an async server component that first awaits `connection()` from `next/server` (so it is never prerendered at build time, when the database may not exist) and is wrapped in `<Suspense>` with a loading fallback. This pattern is valid whether or not the scaffold enabled `cacheComponents`. After each action the server calls `revalidatePath("/")`. Do **not** add `export const dynamic`, `"use cache"` or `revalidate` exports to `page.tsx`.

### Component hierarchy
```
layout.tsx (server)        <html lang="en"> skip link, body
└─ page.tsx (server)       <main id="main"> <h1>Tasks</h1>
   ├─ AddTaskForm          (client leaf — useActionState)
   └─ <Suspense fallback="Loading tasks...">
      └─ TaskList (async server; await connection())
         ├─ empty state <p> "No tasks yet. Add your first one above."
         └─ <ul> TaskItem × n (server)
            ├─ <form action={toggleTaskAction}> button "Mark done" / "Mark not done"
            └─ <form action={deleteTaskAction}> button "Delete"
error.tsx (client)         route error boundary with a "Try again" button
```

### State management
All state is server state in SQLite. The only client state is the add form's `useActionState` result. No global store, no query cache, no `useEffect` data fetching.

### Loading, empty, and error states
- **Loading:** `<p role="status">Loading tasks...</p>` as the Suspense fallback.
- **Empty:** `No tasks yet. Add your first one above.` rendered instead of the list when zero live tasks exist.
- **Error:** `src/app/error.tsx` shows `Something went wrong`, the sentence `The task list could not be loaded.` and a `Try again` button calling `reset()`.

  ```sh
  #!/bin/sh
  # Starts the production server and checks it answers on 127.0.0.1:3000 and listens on loopback only.
  # Requires a prior `pnpm build`. Uses ss (Linux) or lsof (macOS). Port 3000 must be free.
  set -eu
  ./node_modules/.bin/next start -H 127.0.0.1 -p 3000 &
  server=$!
  trap 'kill "$server" 2>/dev/null || true' EXIT
  attempts=0
  until curl -fs http://127.0.0.1:3000/api/health >/dev/null 2>&1; do
    attempts=$((attempts + 1))
    if [ "$attempts" -gt 30 ]; then
      echo "server did not answer on 127.0.0.1:3000" >&2
      exit 1
    fi
    sleep 1
  done
  curl -fs http://127.0.0.1:3000/api/health | grep -q '"status":"ok"'
  if command -v ss >/dev/null 2>&1; then
    listeners=$(ss -ltn)
  else
    listeners=$(lsof -nP -iTCP:3000 -sTCP:LISTEN)
  fi
  if printf '%s\n' "$listeners" | grep -E '(0\.0\.0\.0|\*|\[::\]):3000' >/dev/null; then
    echo "server is listening beyond loopback" >&2
    exit 1
  fi
  printf '%s\n' "$listeners" | grep -q '127\.0\.0\.1:3000'
  echo "ok: health answers and the server listens on 127.0.0.1 only"
  ```
Then run `pnpm format`.

  import { and, asc, desc, eq, isNull, sql } from "drizzle-orm";
  import type { Db } from "@/server/db/client";
  import { tasks } from "@/server/db/schema";

  export type Task = typeof tasks.$inferSelect;

  export function listTasks(db: Db): Task[] {
    return db
      .select()
      .from(tasks)
      .where(isNull(tasks.deletedAt))
      .orderBy(asc(tasks.isDone), desc(tasks.createdAt), sql`rowid desc`)
      .all();
  }

  export function addTask(db: Db, title: string, now: Date = new Date()): Task {
    return db
      .insert(tasks)
      .values({ title, createdAt: now, updatedAt: now })
      .returning()
      .get();
  }

  export function setTaskDone(
    db: Db,
    id: string,
    isDone: boolean,
    now: Date = new Date(),
  ): boolean {
    const result = db
      .update(tasks)
      .set({ isDone, completedAt: isDone ? now : null, updatedAt: now })
      .where(and(eq(tasks.id, id), isNull(tasks.deletedAt)))
      .run();
    return result.changes > 0;
  }

  export function deleteTask(db: Db, id: string, now: Date = new Date()): boolean {
    const result = db
      .update(tasks)
      .set({ deletedAt: now, updatedAt: now })
      .where(and(eq(tasks.id, id), isNull(tasks.deletedAt)))
      .run();
    return result.changes > 0;
  }

#### Step 5 — Validation and server actions

**Do**
Create:
- `src/lib/validation.ts`:
  ```ts
  import { z } from "zod";

  export type Result<T> = { ok: true; data: T } | { ok: false; error: string };
  export type AddTaskState = { error: string | null; title: string };

  const titleSchema = z
    .string()
    .trim()
    .min(1, "Enter a task.")
    .max(200, "Keep it under 200 characters.");
  const idSchema = z.uuid();

  export function parseTitle(value: unknown): Result<string> {
    if (typeof value !== "string") {
      return { ok: false, error: "Enter a task." };
    }
    const parsed = titleSchema.safeParse(value);
    if (parsed.success) {
      return { ok: true, data: parsed.data };
    }
    return { ok: false, error: parsed.error.issues[0]?.message ?? "Enter a task." };
  }

  export function parseId(value: unknown): Result<string> {
    const parsed = idSchema.safeParse(value);
    return parsed.success
      ? { ok: true, data: parsed.data }
      : { ok: false, error: "Invalid task." };
  }
  ```

## 13. Testing Strategy

| Layer | Framework | What it covers | Where | Runs |
|---|---|---|---|---|
| Static | `tsc`, Biome | Types and lint across the repo | whole tree | `pnpm typecheck`, `pnpm lint` |
| Unit | Vitest | Health route, validation rules, palette contrast | `tests/unit/` | `pnpm test` |
| Integration | Vitest | Migrations and every query against a real, freshly migrated SQLite file | `tests/integration/` | `pnpm test` |
| E2E | Playwright (Chromium) | The page shell, list states, add, done/undo, delete, keyboard operation, target size, reflow | `tests/e2e/` | `pnpm test:e2e` |

### Critical flows to cover E2E
1. Add a task → it appears → reload → still there.
2. Mark done / undo / delete, including that delete keeps the row.
3. The whole flow with the keyboard only.

### Test data
Integration tests create a temp directory per test, open a new SQLite file there, apply the committed migrations and delete it afterwards (`tests/helpers/test-db.ts`); no test shares state. E2E runs against `data/e2e.db`, which Playwright deletes and re-migrates before starting the server; each spec starts with `resetTasks()` and inserts rows with `seedTask()` (`tests/helpers/e2e-db.ts`). The local services for these tests are files, not processes, so there is nothing to provision beyond `pnpm db:migrate` (run by the Playwright `webServer` command). The variable pointing at the E2E database is `DATABASE_PATH`, set in `playwright.config.ts`.

### What is deliberately not tested
The error boundary's rendering (no safe way to force a failure without test-only code; step 6 asserts only that the file exists and has the client directive), the loading fallback, light/dark beyond the body background, and any browser other than Chromium. Server actions are covered end to end, not in isolation.
